# ADR-0019: Дедупликация client tools по `(kind, name, schema_hash)`

- Статус: `accepted`
- Дата: `2026-04-28`

## Контекст

Менеджер агрегирует tools из подключённых 1С‑клиентов и публикует их AI‑агенту через MCP. На реальных прогонах одновременно живут несколько однотипных сессий (например, 5 `vanessa_test_client` в одном VA‑прогоне). Если каждую сессию публиковать в `tools/list` отдельно, AI‑агент получит десятки квази‑дубликатов с разными `session_id` в имени, что:

- засоряет `tools/list` и съедает context window клиента;
- мешает AI‑агенту выбирать «куда вызвать» — приходится сравнивать суффиксы id;
- ломает stable tool naming — каждая новая сессия меняет состав tools.

Альтернативы:

- Публиковать каждую сессию отдельным tool `<kind>__<session_id>__<tool>`. Засоряет list, нестабильные имена.
- Публиковать union‑схему по всем сессиям одного kind. Технически неустойчиво при разных схемах.
- Не публиковать client tools в `tools/list` вообще, оставить только `session.call`. Лишает MCP‑клиентов нативного UX.

## Решение

Схлопывать однотипные регистрации client tools в один публичный tool, ключ дедупликации — кортеж `(kind, tool_name, schema_hash)`.

1. Если несколько сессий одного kind зарегистрировали tool с одинаковыми `tool_name` и `input_schema` (одинаковый `schema_hash`) → публикуется **один** tool с именем `<kind>__<tool_name>`.
2. Менеджер оборачивает оригинальную `input_schema`, добавляя поле `session_id: string`:
   - если активна ровно одна сессия kind → `session_id` опционален, по умолчанию = эта сессия;
   - если две и более → `session_id` обязателен; вызов без него возвращает структурную ошибку с ссылкой на `session.list`.
3. Переход «1 ↔ N сессий» пересчитывает `required` и эмитит `notifications/tools/list_changed`.
4. Если две сессии того же kind зарегистрировали один и тот же `tool_name` с **разными** схемами → дедупликация невозможна, публикуются раздельно с дизамбигуирующим суффиксом `<kind>__<tool_name>__s<short_id>`. Это edge case.
5. Server tools, ClientLocal tools и Management tools не дедуплицируются (kind в имя не подмешивается).
6. Универсальный fallback `session.call(session_id, tool_name, arguments)` доступен всегда — для MCP‑клиентов без `tools/list_changed` и для edge case'а с разными схемами.
7. `schema_hash` — стабильный хэш канонизированного JSON Schema (canonical JSON, sort keys, без поля `$id`). Конкретный алгоритм фиксируется реализацией этапа 2.

## Следствия

### Положительные

- Стабильный, читаемый `tools/list` независимо от количества параллельных сессий.
- AI‑агенту требуется один лишний параметр `session_id` только когда есть реальная неоднозначность.
- Edge case с разными схемами не теряется и не маскируется — он становится видимым через явный суффикс.
- Совместимость с MCP‑клиентами, не понимающими `tools/list_changed`, обеспечена через `session.list` + `session.call`.

### Отрицательные / стоимость

- Менеджер модифицирует `input_schema` (вносит `session_id`) — клиент должен не падать на нём при дальнейшем routing'е (менеджер удаляет поле перед отправкой).
- Требуется надёжная канонизация JSON Schema для `schema_hash`; ошибки канонизации приведут к ложным «edge case» дубликатам или к неожиданному merge.
- Поведение «опционально/обязательно» на `session_id` динамическое — клиенту, кэширующему схему, нужно реагировать на `tools/list_changed`.

### Неграницы

- ADR не фиксирует семантику kind'ов (см. §8 спеки).
- ADR не определяет дедупликацию resources/prompts — она ленивая (см. §10.2 спеки и Q‑R3).
