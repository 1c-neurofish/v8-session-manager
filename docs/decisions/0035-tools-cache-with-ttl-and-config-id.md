# ADR-0035: Кеш проксированных тулов на менеджере с TTL и `config_id`

- Статус: accepted
- Дата: 2026-05-06 (proposed) → 2026-05-11 (accepted)
- Контекст задачи: stabilization после ADR-0026/0034 — устранение race-окна на старте MCP-клиента и провалов между переподключениями live-сессий
- Реализация: `tasks/tools-cache-adr0035-20260511/` (design.md, developer-code-context.md, tester-context.md); cargo test `--all` 107/107 passed

## Контекст

Согласно ADR-0034 менеджер публикует в `tools/list` ровно один встроенный tool (`session_list`) плюс проксированные тулы клиентов — top-level `<prefix>__<tool>`. Источником этих имён сейчас является **только текущий состав live-сессий** (ADR-0025 — ClientProxy publication). При уведомлениях об изменении состава менеджер шлёт `notifications/tools/list_changed` (ADR-0026).

В реальной интеграции (DRIVE → менеджер → Claude Code) обнаружились два сценария, в которых поверхность `tools/list` для AI-агента «схлопывается»:

1. **Race на старте.** AI-агент (MCP-клиент) подключается к менеджеру в момент, когда ни одного 1C-клиента ещё не зарегистрировано. `tools/list` возвращает только `session_list`. Часть MCP-клиентов реагирует на `tools/list_changed` с задержкой (или вообще не реагирует), и до следующего рестарта диалога/харнесса агент работает с пустой поверхностью прикладных тулов.
2. **Рестарт менеджера.** Если менеджер перезапущен, а live-сессии в этот момент не успели вернуться, MCP-клиент видит «всё пропало» — даже если конфигурация хорошо известна и обычно публикует один и тот же набор тулов.

**Часть MCP-харнесов (в частности Claude Code) нестабильно реагируют на `notifications/tools/list_changed`** — это и есть основная мотивация persistent-кеша помимо race на старте. Авторитетный источник `tools/list`, переживающий рестарт менеджера, снимает зависимость от того, корректно ли клиент обработал нотификацию.

Анти-паттерн: «лечить» это рестартом MCP-клиента или ручным reconnect. Поверхность тулов для одного и того же `(kind, конфигурация)` стабильна между регистрациями (новых тулов не появляется, исчезают они только при изменении состава расширений). Значит можно опираться на **последнее наблюдённое состояние**, не дожидаясь онлайн-сессии, и явно отделять «тула нет в реестре» от «тул есть, но сейчас никто его не обслуживает».

Дополнительно: один менеджер обслуживает разные конфигурации 1С (DRIVE, УНФ, PAM, …). У них разный набор расширений, значит — разный набор тулов. Кеш должен быть **per-configuration**, а не один глобальный.

## Решение

Менеджер ведёт **persistent кеш проксированных тулов** с TTL, ключевой по паре `(kind, config_id)`. Кеш используется как источник `tools/list`, в `tools/call` он валидируется наличием live-сессии и отвечает явной ошибкой, если live-сессии нет.

### Структура кеша

```rust
struct ToolsCacheEntry {
    cache_key: (String /* kind */, String /* config_id */),
    tools: Vec<ToolSpec>,         // дословно как пришло в session.register
    last_seen_at: DateTime<Utc>,  // bump'ится только на register
}
```

Хранилище: `workPath/tools_cache.json` (атомарная запись через staging file + rename, как в ADR-0015) + копия в памяти. Загрузка при старте менеджера, сохранение — после каждого изменения (replace/eviction/reset).

### `cache_key`

- `kind` — берётся как и раньше из `session.register`.
- `config_id` — **новое опциональное поле в payload `session.register`**. Источник значения определяет BSL-сторона (см. раздел «Декомпозиция»). Если клиент не передал `config_id` — менеджер подставляет `config_id = kind` (обратная совместимость с уже задеплоенными расширениями).

Имена префиксов в `tools/list` остаются `<kind>__<tool>` — т.е. публичный namespace тула не меняется. `config_id` влияет только на ключ кеша и поведение reset/TTL. Пересечение тулов между разными `config_id` одного `kind` не ожидается на текущих кейсах; если возникнет — поведение определяется ADR-0019 (дедупликация по `(kind, name, schema_hash)`), это вне scope ADR-0035.

### Поведение `tools/list`

1. Lazy-cleanup: пробег по кешу, eviction записей с `now - last_seen_at > cache_life_period` (запись на диск только если что-то выкинули).
2. Возврат: `session_list` + объединение `tools` всех оставшихся записей кеша.
3. **Live-сессии не обязательны.** Кеш — авторитетный источник для `tools/list`. ADR-0026 (политика `tools/list_changed`) сохраняется для случаев, когда состав меняется (добавилась запись, прошёл eviction, выполнен reset).

### Поведение `tools/call`

Алгоритм при вызове `<kind>__<tool>(args)`:

1. Найти live-сессию с этим `kind` через `SessionDispatcher` (ADR-0024).
2. Если есть — форвардить вызов как сейчас.
3. Если нет — вернуть **MCP tool error** (а не JSON-RPC `method not found`):
   ```json
   {
     "content": [{
       "type": "text",
       "text": "Tool '<kind>__<tool>' is currently unavailable: no live session of kind=<kind>."
     }],
     "isError": true,
     "_meta": {
       "error_code": "no_live_session",
       "kind": "<kind>",
       "tool": "<tool>"
     }
   }
   ```

Обоснование: тул присутствует в `tools/list`, поэтому JSON-RPC `-32601` (method not found) ввёл бы клиента в заблуждение. `isError: true` — идиоматичный MCP-способ для runtime-ошибок (см. spec); `_meta.error_code` — машиночитаемый дискриминатор для будущих кейсов.

### Обновление кеша

Триггер обновления — `session.register` И `session.tools_changed` (notification от уже зарегистрированной сессии) с непустым полем `tools`. Расширение относительно первоначальной формулировки ADR: без bump'а кеша на `tools_changed` он отстаёт от live-сессии в пределах одной WS-сессии (например, если расширение динамически догрузилось). Решение зафиксировано в `tasks/tools-cache-adr0035-20260511/design.md` §3.3 и закрыто реализацией.

Действия при триггере:

1. Считаем `cache_key = (kind, config_id ?? kind)`.
2. **Replace** запись в кеше: `tools := payload.tools`, `last_seen_at := now`.
3. Если `tools/list` менеджера фактически изменился (set имён или хотя бы одна `inputSchema`) — отправить `notifications/tools/list_changed` всем подключённым MCP-клиентам (поведение ADR-0026 без изменений).
4. Атомарно записать `tools_cache.json`.

`tools/call` **не обновляет** `last_seen_at` — иначе кеш будет «жив» вечно, пока кто-то им пользуется, даже если конфигурация снята (контр-пример: переезд BSL-расширения на другую машину).

### TTL и eviction

- Параметр конфигурации: `tools_cache.cache_life_period`, дефолт `5d`. Формат — humantime (`5d`, `12h`, `30m`).
- Eviction — lazy: проверяется на каждом `tools/list` и каждом `register`. Фоновых таймеров нет.
- Запись с `now - last_seen_at > cache_life_period` удаляется из памяти и из файла. Если после eviction состав `tools/list` поменялся — рассылается `tools/list_changed`.

### Reset (новый системный тул)

Новый встроенный tool `tools_cache_reset`:

```json
{
  "name": "tools_cache_reset",
  "description": "Очищает кеш проксированных тулов менеджера. Без аргумента — полный сброс. С аргументом — сброс записи по config_id.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "config_id": {
        "type": "string",
        "description": "config_id записи кеша (как она видна в session_list/session.register). Если не указан — сбрасывается весь кеш."
      }
    },
    "additionalProperties": false
  }
}
```

Поведение:

- Записи удаляются из памяти и из `tools_cache.json` атомарно.
- Live-сессии **не трогаются**: их тулы перезапишут кеш при следующем `register`/heartbeat-renew, если такая пере-регистрация в протоколе предусмотрена.
- После reset — `notifications/tools/list_changed` всем MCP-клиентам.

`tools_cache_reset` экспонируется только через MCP-поверхность менеджера (по аналогии с `session_list`), CLI-обвязки в этом ADR не описываются.

### Расширение `session_list`

Чтобы агент мог осмысленно вызвать `tools_cache_reset(config_id=…)`, в payload `session_list` добавляется поле `config_id` для каждой сессии:

```jsonc
{
  "sessions": [{
    "session_id": "…",
    "kind": "DRIVE",
    "config_id": "DRIVE",        // ← новое поле
    "state": "active",
    "tools": [ … ],
    // …
  }]
}
```

Дополнительно, для отладки — отдельная команда `tools_cache_inspect` **в этом ADR не вводится**. При необходимости откроется отдельный ADR.

### Конфигурация менеджера

Минимальное расширение `manager.yaml` / `v8sm.yaml`:

```yaml
tools_cache:
  enabled: true
  cache_life_period: 5d
  storage_path: ${workPath}/tools_cache.json   # дефолт; настраивается
```

Если `enabled: false` — поведение деградирует к ADR-0034 (только live-сессии), кеш не пишется и не читается. Дефолт — `true`.

## Декомпозиция по компонентам

Изменения распределяются между тремя репозиториями:

### 1. `v8-client-session-manager` (Rust, основная работа)

- Расширить парсинг `session.register` payload: опциональное `config_id: Option<String>`.
- Реализовать `ToolsCacheStore` (память + JSON-файл, атомарная запись).
- Подключить `ToolsCacheStore` к `tools/list` (источник имён) и к `tools/call` (валидация live-сессии + ответ `no_live_session`).
- Lazy eviction по TTL.
- Новый встроенный tool `tools_cache_reset`.
- Расширить `session_list` payload полем `config_id`.
- Конфигурационная секция `tools_cache` в YAML менеджера.
- Тесты: интеграционные (роняем live-сессию → `tools/list` остаётся, `tools/call` → `no_live_session`; рестарт менеджера → кеш живёт; eviction по TTL; reset по `config_id`).

### 2. `web-transport-addin` (Rust, минимально)

Сама внешняя компонента — это транспорт/каркас сообщений. Она **не должна знать** про `config_id` как смысловое поле. Достаточно убедиться, что:

- payload `session.register`, который BSL передаёт в addin, доезжает до WS-сообщения дословно (как сейчас) — лишних полей не теряется.
- Если из addin'а есть строгая JSON-схема payload'а `register` — добавить в неё опциональное поле `config_id: string`.

Если payload передаётся прозрачным `serde_json::Value` (наиболее вероятно по текущему коду) — изменений в addin не требуется.

### 3. `client_mcp` (BSL-расширения: DRIVE, UT, PAM, …)

- Добавить в формирование `session.register` поле `config_id`.
- Источник значения — **константа уровня расширения** или метаданные конфигурации. Конкретный механизм фиксируется в спеке/Phase 1 (см. «Открытые вопросы»). Базовый дефолт без правок BSL — отсутствие поля → менеджер подставит `kind`.

Изменения в BSL точечные и параллельны для каждой конфигурации (DRIVE/UT/PAM). На стороне ADR-0035 BSL-сторона не блокирует поставку: менеджер работает корректно и без `config_id` (fallback `config_id = kind`).

## Порядок поставки

1. **session-manager (этот репо).** Изменения покрывают smoke без правок BSL/addin за счёт fallback'а.
2. **web-transport-addin.** Только если выявится потеря поля при transparent forwarding (маловероятно).
3. **client_mcp BSL.** По мере того как у конкретной конфигурации появляется второй config с тем же `kind` или нужна тонкая адресация reset — в DRIVE/УНФ/PAM добавляется `config_id`.

Каждый шаг — самостоятельная задача (own spec/task-breakdown), но все три связаны общим контрактом, описанным выше.

## Открытые вопросы

Зафиксированные при acceptance:

1. **Источник `config_id` на BSL-стороне** (open). Менеджер работает с fallback `config_id = kind` — поставка не блокируется. BSL-сторона (DRIVE/УНФ/PAM) дорабатывается отдельной задачей с собственной спекой. Варианты на момент acceptance: (а) константа расширения `client_mcp_ConfigId`; (б) derive из `Метаданные.ИмяКонфигурации + Метаданные.Версия`; (в) `/C config_id=…`.
2. **Изменение `inputSchema` тула между версиями расширения** (closed). Replace на каждом register покрывает кейс автоматически. Детектирование «тул переехал, схема несовместима» — отдельный ADR при появлении кейса.
3. **Reset в распределённом сценарии** (closed). Replace-семантика: выигрывает последний register. Проверено в Phase 4 тестом `concurrent_upsert_under_short_ttl_keeps_store_consistent`.
4. **Honest rmcp HTTP e2e-тест** (open / follow-up). Integration-тесты Phase 3/4 проверяют семантику через прямой вызов `McpToolServer::list_all_tools_inner`. Поднятие реального rmcp HTTP-клиента в test-окружении требует декомпозиции `serve_session_manager` (сейчас монолитный blocking bootstrap) и новой dev-dep. Микро-задача отдельным треком на этап 8; не блокирует acceptance ADR-0035.

## Последствия

### Положительные

- AI-агент видит стабильную поверхность `tools/list` сразу при подключении к менеджеру, не дожидаясь регистрации live-сессии.
- Рестарт менеджера переживает кеш на диске → нет «провала» поверхности тулов в окне переподключения live-сессий.
- Чёткий машиночитаемый ответ `no_live_session` — клиенты могут отделять «нет такого тула» от «никто сейчас не обслуживает».
- Per-`config_id` адресация позволяет одному менеджеру обслуживать разные конфигурации без коллизий.
- TTL ограничивает «зомби-кеш» сроком в 5 суток — устаревшие конфигурации сами выпадают.

### Отрицательные / риски

- Кеш — ещё одно состояние, которое менеджер обязан синхронно поддерживать на диске. Атомарная запись + восстановление нужны.
- Возможен сценарий «кеш обещает тул, но текущая live-сессия его не объявила» — например, если разработчик удалил расширение, не дёрнув reset. Mitigation: `tools/call` всё равно работает (форвард пройдёт в live-сессию, та ответит ошибкой по своей логике); `last_seen_at` не bump'нется → запись просто не обновится и в течение TTL выпадет.
- Совместимость с MCP-клиентами, которые игнорируют `_meta` — текстовое сообщение в `content` остаётся читаемым, поэтому деградация мягкая.

## Связанные решения

- ADR-0019 — дедупликация client tools по `(kind, name, schema_hash)`. Остаётся актуальной — кеш хранит ровно те `ToolSpec`, что прошли дедупликацию на момент register.
- ADR-0024 — per-session dispatcher. Кеш не подменяет dispatcher, только дополняет источник имён.
- ADR-0025 — публикация client tools и резолвинг имени. Имена-префиксы остаются прежними; ADR-0035 меняет только источник истины.
- ADR-0026 — политика `tools/list_changed`. Сохраняется; добавляются триггеры eviction и reset.
- ADR-0029 — расширения payload `session.register`. ADR-0035 добавляет поле `config_id` в ту же зону.
- ADR-0034 — единая MCP-поверхность. ADR-0035 расширяет её с одного встроенного тула до двух (`session_list` + `tools_cache_reset`); это сознательное минимальное расширение, не возврат к множественным managerским tool'ам.

## Проверка

- Сценарий A (race): запустить менеджер без live-клиентов → подключить MCP-клиент → `tools/list` пустой (только встроенные). Подключить DRIVE → MCP-клиент получает `tools/list_changed`. Отключить DRIVE → `tools/list` остаётся прежним; `tools/call DRIVE__find` → `isError: true`, `_meta.error_code = "no_live_session"`.
- Сценарий B (рестарт): зарегистрировать DRIVE → дождаться записи `tools_cache.json` → погасить менеджер → стартовать снова → `tools/list` сразу полный (без live-сессии).
- Сценарий C (TTL): выставить `cache_life_period: 60s` → register → отключить → подождать 90s → `tools/list` без записей DRIVE; в файле кеша запись отсутствует.
- Сценарий D (reset): два разных `(kind, config_id)` в кеше → `tools_cache_reset(config_id=…)` → удалена только указанная запись; `tools/list_changed` отправлен; `tools_cache.json` обновлён атомарно.
- Сценарий E (back-compat): DRIVE BSL без `config_id` → запись в кеше с `config_id = kind`; `session_list[*].config_id == kind`.
