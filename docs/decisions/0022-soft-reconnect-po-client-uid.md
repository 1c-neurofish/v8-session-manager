# ADR-0022: Soft reconnect по `client_uid`

- Статус: `accepted`
- Дата: `2026-04-28`

## Контекст

WS‑соединения 1С‑клиентов с менеджером ломаются в реальной жизни регулярно: сетевой blip, перезапуск addin‑модуля, подвисший `external_event`, временная пауза `1cv8c`. Текущая seedline предполагает, что после разрыва WS:

- VA‑прогон не должен прерываться полностью;
- AI‑агент не должен видеть «пропавшую» сессию, если 1С‑клиент жив и сейчас восстановит соединение;
- in‑flight вызовы корректно завершаются ошибкой, повторное добавление в реестр не должно приводить к дубликатам.

Альтернативы:

- Жёсткий unregister на любой WS‑drop. Просто, но любая сетевая дрожь убивает прогон.
- Persistent registry с переподключением по token. Сложно, требует устойчивого хранилища, выходит за рамки «менеджер ephemeral» (§1 non‑goals).
- Soft reconnect только при наличии auth‑token. Половинчато; в локальной dev‑конфигурации без токена reconnect недоступен, что не отражает реальную потребность.

## Решение

Soft reconnect по `client_uid` с reconnection grace:

1. На WS disconnect сессия переходит в состояние `Disconnected`, запись в реестре сохраняется (`session_id`, набор tools, FIFO‑очередь, счётчики, `last_call_at`). В `session.list` отражается флаг и `disconnected_since`.
2. Все in‑flight `tool.call` к этой сессии завершаются ошибкой `-32011 session_gone`. Очередь после этого опустошается (queued записи отменяются с тем же кодом).
3. Если в течение `reconnection_grace_secs` (default 30) приходит новый WS с `session.register` от того же `client_uid` → менеджер привязывает новый сокет к существующей записи, состояние возвращается в `Active`. В ответе на `session.register` менеджер указывает `reconnected: true`.
4. Если в течение grace новый WS не пришёл → менеджер пытается `child.kill()` (если процесс ещё жив), удаляет запись, эмитит `tools/list_changed`.
5. Если WS жив, но клиент шлёт `session.register` с `client_uid`, который уже **активен** (не `Disconnected`) → ошибка `-32010 session_uid_collision`. Клиент должен сменить uid.
6. Безопасность: при включённом auth‑token reconnect безопасен (uid угадать без токена нельзя). При выключенном — фиксируем риск в audit log; на dev‑стендах (loopback bind) считаем приемлемым.
7. Reconnect не восстанавливает результаты in‑flight вызовов — они уже завершились ошибкой; AI‑агент должен сам перезапросить, если нужно. Это явный контракт.

## Следствия

### Положительные

- VA‑прогоны переживают сетевые blip'ы без полного перезапуска session set.
- AI‑агенту не нужно перерегистрировать tools — `session_id` стабилен через reconnect.
- Простая модель без persistence: всё живёт в памяти, grace ограничен секундами.

### Отрицательные / стоимость

- В отсутствие auth‑token uid → roughly единственная защита; угадать uid за 30 секунд физически возможно (особенно если он короткий или предсказуемый). Mitigation — рекомендация использовать `Новый УникальныйИдентификатор()` (UUIDv4) и включать auth‑token в любой не‑loopback конфигурации.
- In‑flight запросы теряются — это ломает идею «прозрачного» reconnect для AI‑агента. Альтернатива (буферизация и replay) выходит за рамки MVP.
- FIFO/registry должны корректно «приостанавливаться» на время `Disconnected`: новые `tool.call` к такой сессии немедленно возвращают `session_gone`, а не висят.

### Неграницы

- ADR не описывает persistence или восстановление между перезапусками менеджера (§1 non‑goals).
- ADR не вводит token‑based reconnect (только `client_uid` + опциональный auth‑token при handshake).
- ADR не определяет default значение `reconnection_grace_secs` как нормативное — оно конфигурируемо.
