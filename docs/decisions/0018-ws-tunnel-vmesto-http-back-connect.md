# ADR-0018: WS-tunnel вместо HTTP back-connect

- Статус: `accepted`
- Дата: `2026-04-28`

## Контекст

Менеджер клиентских сессий должен общаться с 1С‑процессами (`1cv8c` + `web-transport-addin`) в обе стороны:

1. control‑plane: регистрация сессии, heartbeat, уведомление о смене набора tools, грейс‑шатдаун.
2. data‑plane: проксирование MCP `tool.call` от AI‑агента к конкретной 1С‑сессии и обратный возврат результата.

Альтернативные транспорты:

- HTTP MCP сервер внутри addin'а (текущая реализация `web-transport-addin/src/mcp/`) с back‑connect от менеджера. Менеджер должен открывать HTTP к каждому 1С‑процессу.
- Двунаправленный JSON‑RPC поверх WebSocket (исходящий коннект от 1С).
- gRPC bidirectional streaming.

Реальные ограничения:

- 1С‑клиенты часто запускаются на машинах за NAT/firewall, в контейнерах с непредсказуемой сетью; входящие HTTP к ним недоступны.
- Менеджер должен поддерживать N сессий одновременно — N серверных портов в 1С‑клиентах создают operational нагрузку.
- Маршрутизация по `session_id` к конкретному соединению нужна на каждом вызове.
- В addin'е уже есть `ws_client.rs`, поднимающий исходящий WS, и `mcp::dispatch_request`, способный обработать JSON‑RPC из любого источника.

## Решение

Использовать один WS‑коннект `1cv8c → менеджер` как двунаправленный JSON‑RPC канал и для control‑plane, и для data‑plane:

1. Один порт на стороне менеджера, несколько исходящих коннектов с 1С‑машин.
2. Каждое сообщение — JSON‑RPC 2.0 поверх WS Text Frame; направления `client → manager` и `manager → client` обслуживаются одним соединением.
3. HTTP MCP сервер в addin'е для сценария «менеджер сессий» не используется; для других сценариев он остаётся.
4. Маршрутизация в менеджере: `session_id ↔ WS connection` 1‑к‑1.
5. Регистрация (`session.register`) — первое сообщение клиента после WS handshake. До получения `result` менеджер не считает сессию активной.
6. Auth — опциональный bearer‑токен в WS handshake; bind на loopback/приватную сеть.

## Следствия

### Положительные

- Снимаются проблемы NAT/firewall и контейнеризации на стороне 1С.
- Менеджер имеет один сетевой endpoint, что упрощает деплой и observability.
- Естественно поддерживается soft reconnect по `client_uid` (см. ADR-0022): тот же сокет, та же запись в реестре.
- Переиспользуется уже существующий `ws_client.rs` в addin.

### Отрицательные / стоимость

- Нужно ввести «server mode» в WS‑клиенте addin: принимать MCP JSON‑RPC из incoming text frames и роутить в `mcp::dispatch_request`. Это доработка, описанная в §13.1 спеки.
- Локальный HTTP MCP сервер addin'а становится «вторым путём» — для нашего workflow ненужным; нужно явно зафиксировать, что в режиме `session_manager` он не активен.
- Один WS — единая точка отказа на сессию; компенсируется reconnect‑grace (см. ADR-0022).

### Неграницы

- Этот ADR не предписывает конкретный фрейминг сообщений (см. §4.2 спеки) и не фиксирует TLS‑политику (см. §11).
- Не заменяет MCP HTTP/stdio контракт между AI‑агентом и менеджером — это про канал addin↔manager.
